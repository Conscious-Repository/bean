# Decisions

Every choice made where the spec was silent, every spec error found, and every design decision, numbered in the order they were made. Code comments and other documents cite them by number ("DECISIONS 76").

The rule: follow the spec's DEFAULT; if there is none, pick the simplest deterministic rule, write it here, and continue.

Entries before 105 use the old command name `hlog`. Section numbers are those of SPEC.md at the time of the entry.

## M1 (bytes)

1. **Module name.** The folder and Go module are `bean`. The CLI stays `hlog` as SPEC.md 12 says, until the project takes its neutral name.

2. **What counts as an "integer" for the ±(2^53−1) rule (SPEC 4.1).** The spec rejects "an integer outside the range" but does not say whether `9.007199254740992e15` (an exponent literal with an integral value) is an integer. Choice: a number is an integer when its *canonical form* is an integer literal, which is any integral double with magnitude below 1e21 (ES toString switches to exponent form at 1e21). So `9007199254740992`, `9.007199254740992e15` and `9007199254740992.0` are all `bad number`; `1e21` is accepted and canonicalizes to `1e+21`. This makes the writer and the parser agree by construction. Vector V1 pins it. Proposed spec text: "An integer is a number whose canonical form (4.1 rule 7) has no `.` and no `e`."

3. **Error priority when a file has several faults (SPEC 3.8 steps 3–6).** The parser reads the whole file once and reports the fault that comes first in the validation order: `bad json`, then `duplicate key`, then `bad number`, then `bad string`. A structural fault stops parsing, so a duplicate key after a syntax error is never seen; this matches "stop at the first failure".

4. **Nesting depth.** Not in the spec. The parser refuses more than 256 levels with `bad json` (denial-of-service guard, same spirit as the 1 MiB limit). Propose adding to 15 (Security).

5. **P-256 signing nonces.** The software signer uses Go's `ecdsa.Sign` (random nonce), then normalizes to low-S. RFC 6979 is a SHOULD; it is not in the standard library and would need a dependency or a hand-rolled HMAC-DRBG. Deferred; verification is unaffected. Vector V6 therefore records *a* valid low-S signature, and the checker verifies it rather than recomputing it.

6. **`elliptic.UnmarshalCompressed` is marked deprecated in Go** but is the only standard-library way to parse a SEC1 compressed point in Go 1.24. Kept. Revisit when `ecdsa.ParseUncompressedPublicKey`-style helpers cover compressed points.

7. **AES-SIV is hand-rolled** per the brief (constraint 6). The v0.4 change set (C3) allows a vetted library instead. The RFC 5297 A.1 and A.2 vectors pass, and the Python checker (OpenSSL's AES-SIV) agrees on V11 including a 1 MiB blob, so the hand-rolled version stays until someone names a library they prefer.

8. **BIP-39 word list license.** The list is from bitcoin/bips, `bip-0039/english.txt`, SHA-256 `2f5eed53…dbda` (matches the checksum published in the BIP-39 wordlist README). BIP-39 is BSD-2-Clause. Recorded in `core/bip39.go`. (Corrected 2026-10-30: the BIP header says `License: MIT`; see NOTICE and 120.)

9. **`WordsToSeed` lowercases and trims each word.** The spec does not say. Rationale: paper is read aloud and typed by hand.

10. **Vector V4 uses fixed nonces** (`…0001`, `…0002`, `…0003`) so the vector is reproducible. Real writers use `NewNonce`.

## Spec errors found

- SPEC 14 V1 lists "the RFC 8785 number samples". Two of those samples are commonly misquoted; the authoritative strings for `0x41b3de4355555556` and `…57` are `333333333.3333334` and `333333333.33333343`. Both Go `strconv` and Python `repr` agree. The vector file carries the literal inputs rather than the bit patterns, so there is nothing to misquote.

## M2 (verifier)

11. **Successions are built in M2, not M5**, using the seed-only rule from the v0.4 change set (C5 to C11). With no current-signed successions the tree code is about 60 lines, so a stub would have cost more than the real thing. If the meeting restores current-key rotation, `checkSuccession` and the fork branch of chain selection are the only places that change.

12. **Size check order (C6).** The 16 MiB succession limit is applied before parsing (step 2) and the 1 MiB record limit after the type is known (step 8), both with `too large`. The spec puts the size check at step 2 only, which cannot know the type yet.

13. **Purged targets in the summary.** 12.1 counts valid, invalid, skipped, held and duplicate. A purged target is none of these ("not valid data"). It is left out of every count. Propose adding `<p> purged` to the summary line.

14. **Records of a too-new identity are counted as skipped**, along with the unknown-version files themselves. 8.2 says "do not evaluate"; skipped is the nearest bucket.

15. **Held destructive records and `superseded by sibling` are warnings on the record, held records stay valid**, as 6.6 and 6.7 say. A held tombstone's target does not exist locally, so there is nothing to purge until sync (7.5, M3).

16. **A tombstone of an invalid record still purges it.** 6.7 does not say whether the target must be valid. Simplest rule: the bytes are hidden either way, which is what the person wanted.

17. **`frozen` for off-chain keys.** 5.7 item 4 says claims signed by keys below the lowest common ancestor are `frozen`; a key that was never in the tree stays `key not in chain`. The verifier keeps both strings.

18. **Blob checks (`blob corrupt`, `blob missing`) are not in `VerifyFiles`.** They need the `blobs/` directory and belong to the folder layer (M3). `VerifyFiles` depends only on the record files, which keeps 6.2 literally true.

## Canon from the design review of 2026-10-27

Recorded so the build reflects it. The eight one-pager questions were not reviewed; they stay open.

- **"This is just file storage."** Hash every file, address by hash, never edit, add new files. Confirms section 7. Where the folder lives (disk, S3, CDN) is outside the core.
- **Identity.** The proposed default is a Nostr keypair (npub/nsec) with NIP-46 remote signing and re-sign-everything on custodian exit. The genesis-hash identity was not discussed. Open: should the signing key be allowed to be a secp256k1 Schnorr key so one identity flows through relays and signers? That needs a dependency (no stdlib support). Decision pending.
- **Sharing** is a routing problem (grant a known identity access to a known file). Two patterns: login page on a privileged server, or security in the file. Out of scope for v0, confirmed.
- **Schema.** Needed; make it expandable; optional fields are null when absent. Add an adapter-level convention for measurement uncertainty (coefficient of variance) for the NMR source; not core.
- **Claims.** Every record is a claim, including device readings. Vocabulary stands.
- **Trusted devices.** Sign with a tool once at setup; it writes until revoked. Extension 2 (device.pair) matches.
- **Interpretation loop.** Blob in; person or AI returns an interpretation claim that references it (`about`). Already supported.
- **First use case.** Whoop JSON via API, pulled on a schedule. M4 target confirmed.
- **Event-driven** downstream processing preferred over cron. App layer; the index could expose a change feed later.
- **Naming.** Say "core", not "kernel".

## M3 (folder and sync)

19. **Hidden targets live in `local/hidden/<64hex>.json`.** The spec says "hide" without saying how. Moving the file out of `objects/` means sync tools and the verifier of other replicas never see it, and a restore is a rename back. Hidden files are still fed to the local verifier so the tombstone's subject check (6.7) can run.

20. **A local purge leaves no hold entry.** 7.6 step 1 erases at once, so there is nothing for gc to do. The tombstone alone carries the fact.

21. **Sync reads the source with the same loader as the destination**, so the source's hold rules run on the source folder. Syncing from a read-only medium would fail on the first hidden write; add a `-read-only` source mode if that comes up.

22. **`local/cache/index.json`** is the canonical bytes of `{"spec", "records": [...]}` sorted by id with type, subject, author, kid, times, system, ref, valid, hidden, superseded_by, purged_by and error. It is the only index in v0. Query format stays an open question (readers decide).

23. **Export manifest says `hlog-core-v0.4`.** The spec text says v0.3; the string tracks the spec version the writer implements.

24. **`Sync` returns a `Replaced` count** for C13 replacements, in addition to the three counts of 12.3.

## M4 (CLI and CSV adapter)

25. **`hlog blob get <id>`** is added (not in 12.3). Export covers exit, but a person who wants one raw file back should not need a whole export.

26. **CSV adapter fields.** `value` parses as a number into `{"n": ...}`, else as `{"text": ...}`; empty is `{"n": null}` (9.6). Unknown columns are copied into `context` as strings. Identical readings without a native id get increasing occurrence numbers within one file so they are not merged (4.8 rule 6).

27. **`hlog append` prints the counts before the error** when it stops early, since records before the error stay written (12.3).

28. **Exit codes for `purge`, `append`, and others** are 1 on any error; only `verify` uses 3 and 4. `fail()` maps a `too new:` or `compromised:` message to 3 or 4 for commands that surface them later (M5).

## M5 (rotation)

29. **One command, `hlog rotate`, reads the 24 words on stdin.** `hlog recover` is gone (C5). The recovery generation is the position of the head in the chain, so the person never types a generation number.

30. **Seals default to all valid destructive records of the outgoing key in this replica**; `-no-seal <id>` excludes one. A destructive record on another replica that was not synced first is `not sealed` afterwards, which is why the command prints "sync all devices before you rotate".

31. **Sync converges in two passes** when a succession and a tombstone it invalidates travel in the same sync: the tombstone set is computed before copying (7.4 step 2), so the target comes back on the next pass (7.4 step 5). Spec-correct; recorded because it surprised a test.

32. **The paper words are parsed leniently**: numbering like "1." is dropped, case is ignored. The init output can be pasted back as is.

## M6 (read and manual entry, docs/ROADMAP.md)

33. **`hlog add` with no `-at` sets `times.observed` to now at minute precision.** SPEC 3.5 says a writer MUST NOT guess a time. A person typing a symptom reports the present, so now is their claim, not a guess. Adapters still write null for a missing source time.
34. **`hlog ls` and `hlog show` read the verified folder, not `local/cache/index.json`.** They call the same loader as `verify`, so they cannot show a stale or edited cache. Cost: every `ls` checks every signature. Revisit with a real Apple Health import.
35. **`hlog ls` shows only current records by default:** valid, not hidden, not superseded, not a duplicate, not an `hlog.*` record. `-all` adds superseded, duplicate and core records. Purged and invalid records are never listed; `verify` reports those.
36. **Times in `ls` are local, and `-since`/`-until` use the local zone for dates.** A record keeps its own offset on disk; only the display converts.
37. **`hlog show` and `-about` take an id prefix of 6 or more hex digits.** An ambiguous prefix fails with `ambiguous id: <prefix>` (a new error string, CLI only).
38. **Manual values:** a number becomes `{"n", "unit"}`, `true`/`yes`/`false`/`no` become `{"b"}`, anything else `{"s"}`. NaN and infinities stay text. The note goes in `context.note`; `source` is `{"system":"self","adapter":"hlog@0.4.0","ref":null}`, so manual entries never dedupe.

## M9 (hlog mcp, docs/ROADMAP.md)

39. **The MCP server is read-only.** Five tools: `list_types`, `query_records`, `stats`, `get_record`, `read_blob`, all marked `readOnlyHint`. A write tool (an AI adding a note) waits until npub signing exists, so an agent can sign as its own identity rather than the person's (agents get their own key).
40. **Every tool call loads and verifies the folder**, like `hlog ls`. A record added while the server runs shows on the next call. Cost grows with the log; revisit after the Apple Health import.
41. **`read_blob` serves only blobs that a current record names.** A blob whose records are all purged is refused even before `gc` erases it.
42. **`stats` reads only `value.n`.** Series blobs (`value.blob`) and text are counted as `non_numeric`. Mixed units are reported with a warning, never converted. Buckets use the local zone; weeks start on Monday.
43. **Protocol version:** the server answers with the client's version when it is one of 2024-11-05, 2025-03-26, 2025-06-18 or 2025-11-25, else 2025-06-18. Newline-delimited JSON-RPC on stdio; nothing else is written to stdout.

## M7 (Labcorp adapter, docs/ROADMAP.md)

44. **PDF text comes from `pdftotext -layout` (poppler), run as a separate program.** Go's standard library cannot extract PDF text, and a PDF parser would be the biggest dependency in the repo. The adapter also accepts the text file, so a person without poppler can run pdftotext elsewhere. Superpower panels are Labcorp reports, so one adapter covers them.
45. **Types are `lab.<slug of the Labcorp test name>`, with no LOINC codes.** The patient report prints no codes, and mapping from memory is the thing the brief forbids. Results from Quest or another lab will not share types with Labcorp until a mapping file exists.
46. **Native id is `<specimen id>/<test name>`.** The specimen id reaches `hlog append` only inside `source.ref_input` and is gone after the HMAC. Patient name, birth date, patient id, account number and physician are never copied. A test checks this.
47. **Collection time.** The report prints "Date Collected: MM/DD/YYYY HHMM Local" with no zone. Without `-tz` the adapter writes the day (`T00:00:00Z`, precision `day`) and keeps the printed time in `context.raw_time`. With `-tz <IANA zone>` it writes the minute in that zone. The first real report tested also says the requisition had no collection time and the receipt date was used; that note goes in `context.report_note` on every record.
48. **Values.** A plain number is `{"n", "unit"}` and the printed digits are kept in `context.raw_value` when they differ (`1.190`, `3.0`). Anything else is `{"s"}` (`<0.5`, `Negative`). A test the lab did not perform is `{"n": null}` with the lab's reason in `context.lab_comment`.
49. **Units and reference intervals are told apart by column.** Measured on the real report: units start 18 to 25 columns left of the "Reference Interval" header, intervals 3 to 8 columns right of it. The cut is 8 columns left of the header. The "Previous Result" column goes to `context.previous_result` as printed; no real report with previous results has been seen yet.
50. **The lab order PDF is not imported.** It holds no results. Store it with `hlog blob put` if the paper trail matters.
51. **`hlog ls` shows `context.flag`** after the value (`9.9 mg/dL  High`, a made-up example) and prints `no value` for `{"n": null}`.

## Restore (before M8)

52. **`hlog restore` rebuilds `local/` on a new host from the 24 words and a synced copy of `objects/` and `blobs/`.** SPEC 5.5 assumed the device still had `local/identity-secret`, so a lost laptop with only the paper and a backup had no way back. Restore finds the genesis whose `value.recovery` is the commitment to recovery generation 0 of the words, writes the identity secret, and then rotates exactly as `hlog rotate` does (same generation rule, same default seals, `-no-seal`). The lost key stops being the head key, so it can no longer delete or correct; its claims stay valid (6.5). Proposed spec text: a new 5.10 "Restore on a new host".
53. **Restore always rotates.** The old signing key is on the lost host, and a key that may be in someone else's hands should not stay the head key. There is no restore-without-rotate.
54. **`local/identity` is written last.** Until it exists the folder reads as `not initialized`, so a restore that fails halfway can run again. A failed restore that already wrote its succession just adds one more generation on the retry; it never forks.
55. **New error string `input missing: genesis for these words`** when the folder has no genesis for the words (wrong log, or nothing synced yet). Wrong or misspelled words stay `seed does not match`.
56. **A stale backup can freeze the identity.** If the folder lacks a succession that another device wrote, restore writes a second child of an older node; when the two meet, that is a fork and the identity freezes (5.7). The command says "sync every copy of the log you still have into this folder first" before it reads the words.

## Spec error found while testing M6

57. **Step 12 (duplicates) hid parser fixes about half the time.** A fix made with `source.supersedes_ref` (9.7) keeps the dedupe ref of the record it corrects. Step 12 grouped the two and made the lower id the primary, so when the fix had the higher id it became `duplicate:` while the original was superseded, and a reader showed neither. Found as a flaky `TestListHidesSupersededAndPurged`. Fix: step 12 leaves out records that a valid supersede record names. `TestParserFixIsNotADuplicate` fails without the fix. Proposed spec text for 6.3 step 12: "Group valid records that are not superseded by ...". Still open: when two hosts imported the same reading (known limit 4) and one of the copies is then fixed, the unfixed copy and the fix form a group and the lower id wins. Readers may then show the old value.

## M8 (npub signing, SPEC v0.5 change note C21)

58. **An npub signs through a Nostr wrapper event, not the raw record id.** NIP-46 remote signers and NIP-07 browser extensions only sign Nostr events, so a raw BIP-340 signature over the id would keep the nsec on the host forever. The wrapper is `[0, pubkey, created_at, 29944, [], record id]`; its event id is the BIP-340 message. The owner chose this on 2026-10-28.
59. **Kind 29944** is in the ephemeral range (relays do not store it) and is not taken by a NIP we know of. Decided in 87.
60. **`created_at` lives in the sig string** (`secp256k1:<created_at>:<hex>`), because a remote signer may set its own time. The software signer uses 0. It never affects validity. Decimal, no leading zeros, at most 2^53 - 1.
61. **One dependency: `github.com/btcsuite/btcd/btcec/v2` v2.3.4**, which brings `decred/dcrd/dcrec/secp256k1/v4`, `btcd/chaincfg/chainhash` and `decred/dcrd/crypto/blake256`. Hand-rolling BIP-340 point arithmetic was the alternative; a vetted library is safer for signing. `tools/checksecp256k1.py` is a pure-Python BIP-340 that reproduces BIP-340 vector 0, the NIP-19 examples and V18 without sharing any code.
62. **Recovery keys stay Ed25519** from the paper seed. Only signing keys and bare-key authors may be secp256k1. An agent with its own npub can write claims as a bare key (`TestAgentNpubClaim`).
63. **After a rotation or restore, an npub on the chain can never sign that log again** (5.8 key reuse; `rotate` and `restore` now refuse before writing). This is right while the nsec sits in `local/signing-key`: a lost laptop means a lost nsec. It is a reason to give the log a dedicated npub (`init -nostr new`) rather than the person's main one, until NIP-46 signing keeps the nsec off the host.
64. **`init -nostr -` turns terminal echo off with `stty`.** Go's standard library cannot; `golang.org/x/term` would be a second dependency.
65. **The export manifest and index say `hlog-core-v0.5`.** Old exports with `v0.4` import the same way; import-export does not read the string.
66. **`tools/checkvectors.py` uses `public_bytes(Raw, Raw)`** instead of `public_bytes_raw()` so it runs on cryptography before 40. It still needs an OpenSSL with AES-SIV (cryptography 50 in a venv works).

## Agents and chat logging (after M8)

67. **An agent writes as its own bare secp256k1 key, with the person as subject.** Key in `local/agent-key`, one per machine, never synced. SPEC 6.1 already lets anyone add a claim; the verifier already stops a non-author from superseding and a non-subject from tombstoning, so an agent can add but never change or delete the person's records. No spec change.
68. **The person vouches for an agent with an `agent.pair` claim** (`value` = `{key, label}`), the shape of `device.pair` (SPEC 11.3). Readers decide trust; the core does not check pairing. `hlog ls` labels a paired agent's entries `[label]` and an unpaired key's `[unpaired npub1...]`. Unpair by superseding the pair claim with `value.status` = `"unpaired"`, as 11.3 says for devices.
69. **Agent-only replica.** `hlog agent init` works on a synced copy that has no `local/identity`: it takes the only genesis in the folder (or `-identity`), writes `local/identity` and `local/agent-key`, and nothing else. No personal signing key, no paper words. Without `local/identity-secret` the agent cannot attach photos, read blobs, or write `ref_input` (no dedupe key); copying that secret to the agent's machine is an explicit choice, and it opens every blob. Records are plaintext either way, so the agent's machine can read the whole log.
70. **On the person's machine `agent init` pairs at once.** On an agent-only replica it prints the `hlog agent pair <npub>` line to run on the person's machine.
71. **`hlog mcp` is read-only unless `-write`.** With `-write` it makes the agent key on first start (label `agent@<hostname>` unless `-label`) and adds one tool, `log_entry`: type, value (text, number or boolean), unit, at, note, about, details, photo_path. `food.estimate` must have `about`.
72. **Photos must sniff as images** (`net/http.DetectContentType` says `image/*`) and be at most 25 MiB. Without this, `photo_path` plus `read_blob` would let a prompt pull any text file on the machine into the log and back out. They are stored with role `photo`. `read_blob` returns only the size of a binary blob.
73. **The type vocabulary is `cmd/hlog/vocabulary.md`**, embedded in the binary and sent in the MCP instructions so the AI follows it. Conventions only; the core checks none of it.
74. **`ls` hides `agent.pair` and `device.pair`** unless `-all`; they are setup, not events. `-author agent` lists this machine's agent's entries; `-author` also takes an npub.
75. **Writing as the person on an agent-only replica fails** with "no personal key on this replica (agent-only): sign with the agent key instead (-agent)".

## Audit, 2026-10-28

Measured on a 20,000-record log before the pass: `add`, `ls`, `verify` and every MCP call took 4 to 5.5 s, because every command re-proved every signature on one core and opened every file.

76. **Object cache, `local/cache/objects`, the way git's index works.** Records are named by their hash and never edited, so a file whose size and modification time match the cache still holds bytes this replica already proved. Ordinary commands skip only the signature arithmetic for such files; every other check of 3.8 still runs. `hlog verify` ignores the cache, proves every file, and rebuilds it: verify is the fsck. Files modified in the last 2 seconds of wall-clock time are not cached ("racily clean" in git), and an edit that changes size or time is seen at once. An edit that keeps both size and time is seen only by `verify`, as with git. The cache is best effort and never the truth: a missing, garbled or unwritable cache only costs time. Format: one line per canonical record, `<path>\t<size>\t<mtime ns>\t<bytes>`.
77. **Per-file checks (3.8 steps 1 to 15) run on all CPUs.** Results are collected by index, so the report does not depend on scheduling; `VerifyFiles` stays a pure function of the files (G1). `TestParallelMatchesSerial` and the order-independence test pin it.
78. **Writes are durable.** `writeFileAtomic` flushes the temporary file before the rename and the directory after it. On macOS it calls plain `fsync`, not Go's `File.Sync`, which issues `F_FULLFSYNC`: measured 0.02 ms against 3.9 ms per file, and a 20,000-record import went from 11.4 s to 12.0 s instead of minutes. SQLite makes the same choice by default.
79. **`hlog-import-csv` wrote text values as `{"text": ...}`.** SPEC 3.4 says `{"s": ...}`. Fixed, and the CSV time is now kept as written with its own offset instead of converted to UTC. Adapter 0.5.0. This changes the dedupe refs of tuple-keyed rows, which is why it had to happen before any real log existed. The importer now has a test.
80. **`Init`, `Rotate` and `Restore` are one function each**, taking a `NewKey` (the zero value is a new Ed25519 key). The `InitWith`, `RotateTo` and `RestoreTo` variants are gone.
81. **One load per command on the write path.** `Add` resolves the `about` prefix from the same load it appends with; the CLI and the MCP server no longer load first to resolve it. `writerFor` is the one place that picks the person's key or the agent's.
82. **Concurrent hlog processes** (an MCP server beside a CLI) can load at the same moment after a purge arrives. A rename that finds the file already moved is success, and a file that vanishes between listing and reading makes the load list again (up to 5 times). `TestConcurrentLoads` failed without each fix and passes 200 runs and 20 runs under the race detector with them.
83. **`hlog append -agent`** pipes an importer's output in under this machine's agent key. On an agent-only replica it refuses importers that need dedupe refs (no identity secret), with that message.
84. **Leftovers removed:** the `ErrSeedWords` alias (one `ErrSeedMismatch`), `_ = errors.New` in the CLI, an unused field in the Labcorp importer. `Add` moved from `query.go` to `add.go`. `staticcheck` reports nothing; `deadcode` reports only `VerifyFiles`, kept as the pure verifier the spec and a second implementation test against.

After the pass, same log: `ls` 0.43 s (5.5), `add` 0.21 s (4.0), an MCP call 0.23 s (4.0), `verify` 0.6 s warm and 1.2 s cold (4.0). GC tuning was measured and gained nothing, so there is no knob for it.

## CORE.md (2026-10-28)

85. **CORE.md is the protocol in two pages** (about 1,350 words against 14,600 in SPEC.md): only what a second implementation must agree on, plus four open questions. SPEC.md stays authoritative. It was tested by giving a fresh agent only CORE.md and the vectors: its own verifier, with JCS and BIP-340 written from scratch, passed V1 to V5, V7, V12 and V18. The eight things it had to guess (the integer rule, size check order, lowercase signatures, the created_at range, the wrapper serialization, Ed25519 strictness, the dedupe occurrence rule, which hex names the path) are now stated.
86. **V4 now says how its claim's dedupe ref was made**: `source_ref_input` and the V10 dedupe key. Additive; no record or id changed.

## The four open questions, answered (2026-10-28)

Answered from the design review, the project's values and the Nostr specs, so that a reviewer reviews decisions instead of making them. CORE.md section 6 is the short form.

87. **Wrapper kept, with a NIP-31 `alt` tag** `["alt","hlog record signature"]`. Facts: 29944 is not in the NIPs registry (nearest entries 28936 and 30000); NIP-01 says kinds 20000 to 29999 are ephemeral, "not expected to be stored by relays"; NIP-46 permissions take a kind (`sign_event:<kind>`), so a bunker can allow hlog to sign only this kind; NIP-46 does not say a signer keeps the client's `created_at`, which is why it lives in `sig`; NIP-31 says a custom-protocol kind should carry an `alt` tag. The tag changed V18; no real log existed yet. Sources: github.com/nostr-protocol/nips README.md, 01.md, 46.md, 31.md.
88. **Records stay their own format, not NIP-01 events.** Reason: the NIP maintainers prefer local "micro standards" and medical data is the place for one; the existing medical NIPs stalled because maintainers do not want medical data on relays. Records need nested structure, device keys (Ed25519, P-256) and canonical ids independent of the key type. Nostr carries them later, encrypted, for sharing (M10).
89. **Seed-only rotation and freeze-on-fork stay.** They answer the port-out question better than re-signing: a custodian holds the signing key, the person holds the words, and leaving is one rotation with history intact and the custodian's key retired. The point that you can never know a custodian discarded a key is exactly what retiring it by rotation solves. Cost: losing paper and device loses the identity; social recovery can come as an extension.
90. **Freeze criteria:** two weeks of a real log (labs, Apple Health, chat and agent logging) with no change to CORE.md; then `v` = 1 and every DEFAULT final (entry 154 changes this to a freeze at `v` = 0). Sharing, Apple Health batching and the vocabulary sit above the core and do not block it.

## Audit fixes, 2026-10-30

Source: the audit of `b7a1626` (2 blockers, 5 majors, 11 minors, 6 nits). The owner's decision on 112 comes first. The other entries are editor judgement and can be reversed cheaply unless they say otherwise.

106. **Folder lock (B1).** Every command that writes to the folder, and `verify`, takes an exclusive `flock` on `local/lock` (SPEC 7.11). Before this, two `rotate` runs at once wrote two successions off one parent, and that fork freezes the identity for good. Public operations take the lock once, and inner calls use unexported loaders, because flock does not nest per open file. A read-only folder is read without the lock and without side effects. On Windows the lock does nothing (no build there is tested); this is noted in SECURITY.md.
107. **gc and purge fail closed (B2, C25).** Erasure follows record files, not validity: `purge` and `gc` erase only the blobs of the records they erase, and only when no remaining record file names the blob. A loose blob from `blob put` is never erased on its own. `gc` refuses when any identity is too new or the local identity is frozen, because validity can still change then and erasure cannot be undone. Before this, an update or a fork made `gc` erase every blob of the identity.
108. **Writes fail closed (M4).** `append`, `add`, `purge` and the agent writes refuse when the author identity is too new, frozen or unresolved, or when this copy's signing key is not the chain head. `append` refuses identity records. `SignRecord` refuses invalid UTF-8, NaN and Inf. Before this, a write could return an id for a record that `verify` then rejected, so the person thought an entry was stored when no reader would show it.
109. **Restore ambiguity (M3).** A recovery commitment is public, so anyone can copy it into their own genesis. `restore` now fails with `ambiguous: <ids>` when the words match more than one genesis and writes nothing; `restore -identity <id>` picks one. Before this, restore picked the last match in sorted order, so a stranger's file could capture the restore.
110. **Rotation is crash-safe (M5).** The new key goes to `local/signing-key.next` first, then the succession, then a rename. A load finishes the rename when the chain head names the pending key, and deletes the pending key when no chain node names it. Before this, a crash after the succession left a copy whose key was already retired.
111. **Old-format records say so.** A core record with type `hlog.*` fails with `old format` and a hint, instead of a field error. Validity does not change.
112. **Owner decision, 2026-10-30: a retired key writes nothing valid (C26).** Records signed by a retired key after a rotation are invalid. A succession now seals every valid record of the outgoing key, not only the destructive ones, and a record of an older chain key that the next succession does not seal is `not sealed`. SPEC 5.4, 5.5 step 6, 6.3 step 7, 6.5 and CORE.md section 3 change. Compatibility: a log that was never rotated or restored is not affected. On a log that was already rotated with an earlier build, the claims of the old key were not sealed, so they become invalid. One key holds at most about 230,000 records, the size of one succession. CORE.md changed, so the two-week freeze clock (90) starts again.
113. **Duplicates per author (M1, C27).** Duplicate groups are (`subject`, `author`, `source.system`, `source.ref`). Before this, an agent key or any other author could copy the person's ref with a lower id and hide the person's record as a duplicate. `local/purged-refs.jsonl` keeps the per-subject triple, because a purge by the subject should block every re-import about them.
114. **CSV numbers are plain decimals.** `bean-import-csv` keeps `NaN`, `Inf`, hex floats, underscores, overflow and integers of 2^53 or more as text (`{"s"}`), strips a UTF-8 BOM, and refuses invalid UTF-8. Adapter 0.5.1. Rows that earlier builds read as numbers from those spellings get a different tuple ref, so a re-import of such a row adds a new record next to the old one. Plain decimal rows keep their refs. `bean-import-labcorp` refuses invalid UTF-8 (0.1.1).
115. **P-256 signatures use RFC 6979 nonces.** The software signer calls `crypto/ecdsa` with a nil random source (Go 1.24 and later), and derives the public key with `crypto/ecdh` instead of the deprecated `ScalarBaseMult`. V6 is regenerated once, so it is now reproducible; `tools/checkvectors.py` recomputes it with `cryptography`. Old P-256 signatures stay valid.
116. **`init` refuses inside a git work tree** unless `-force`. A commit or a push would publish the keys in `local/` and the plaintext records. The repository `.gitignore` ignores `/objects/`, `/blobs/` and `/local/` as a second guard.
117. **Small hardening.** `blob get` and `PathOf` take a bad id without a panic. `-photo` and the MCP photo path read only regular files, and at most 25 MiB. Stale `.tmp-*` files older than an hour are removed on load. New directories and `local/purged-refs.jsonl` appends are fsynced. Agent labels come only from the local identity's pairings.
118. **`BEAN_NOW` stays.** SPEC 12 documents it as the test clock, and the CLI tests and `demo.sh` depend on it. It changes only the hold clock and `times.imported`, never validity; a person who sets it only changes their own folder.
119. **Commit e3d4ec2 keeps its Co-Authored-By trailer.** Removing it means rewriting published history. New commits have no trailer.
120. **The BIP-39 word list is MIT, not BSD-2-Clause** (correcting 8). The BIP header says `License: MIT`. `NOTICE` carries the MIT permission notice; `core/bip39.go` points to it.
121. **Importers keep numbers that a record cannot carry as text** (round 2 fuzz finding). `1e17` or a 21-digit lab value parses as a float, but SPEC 4.1 allows integer values only up to 2^53, so `append` failed on the whole file. Both importers now check `core.ExactNumber` and write `{"s"}` instead. No stored record changes: such files could not be imported before.
122. **Seal set.** A rotation seals every record of the outgoing key, valid or not, and the target ids of tombstones, supersede records and holds. Sealing only valid records killed the person's own record when they excluded a thief's tombstone with `-no-seal`: the hidden target came back `not sealed`.
123. **A copy may write before its first sync.** With no genesis in the folder, `append` writes (the records are `unresolved author` until the genesis arrives). M4 refuses only when the genesis is present and invalid, too new, frozen, or the key is not the head.

## Round 3, 2026-10-30

124. **Owner decision, 2026-10-30: seal continuations, not a bigger file (C28).** The owner asked for the simplest fix that keeps the design values. One succession holds about 230,000 ids, and C26 made every record of the outgoing key need a seal, so a log with more records could not rotate at all. The fix is the smallest primitive that keeps every existing rule: a new core type `bean.seal`, signed by the same recovery key as its succession, that carries more ids. The succession says how many parts follow (`value.parts`), so a reader knows when the set is complete, and an incomplete set seals nothing (fail closed, nothing erased, `gc` refuses). Raising the 16 MiB limit was rejected: every reader would have to hold one huge file in memory, and the limit would only move. A succession below the limit has no `value.parts` and is byte-identical to before, so no existing record, id, signature, label or vector changes. Builds before C28 cannot read a rotation with parts (`unknown core type`, `bad field: value`). CORE.md changed, so the two-week freeze clock (90) starts again. SPEC 3.3, 5.4, 5.5 step 8, 5.8, 6.3 steps 5b and 7, 6.7, 7.4, 7.6, 12, 13 (tests 39 to 43), 14 (V21), 17.
125. **Crash order with parts (editor judgement).** `rotate` writes `local/rotation-pending` (the succession id), then `local/signing-key.next`, then the parts, then the succession, then renames the key and removes the note. A load that finds the note and no succession file removes the parts that name it: the rotation is undone, the old key is still the head, and `rotate` can run again. A load that finds the succession finishes the rename (110). Tested with crash hooks and a kill loop of 40 runs at random moments. A part only ever reaches another copy without its succession through sync or a copy tool in the middle of a crash; such a part is held and inert, because its succession was never written and cannot be signed again (a new rotation uses a new nonce and key).
126. **Parts per record and the limit (editor judgement).** The writer puts 200,000 ids in the succession and in each part (about 14.6 MB, under 16 MiB), and at most 1,000 parts, so one key holds at most 200,200,000 records. Above that `rotate` fails with `too large` before it writes anything. The chunk size is a package variable that only tests change; there is no flag or environment variable for it.
127. **Sync copies parts first.** `bean sync` copies `bean.seal` files before the other files, so a sync that stops halfway leaves the parts without the succession (held, no effect) rather than the succession without the parts (fail closed until the next sync). The result of a finished sync does not depend on the order.
128. **Seal parts are identity records.** They are not resolved against signing keys, and they cannot be the target of a supersede or a tombstone (`bad target`), so no one can hide a part to break a seal set. They are excluded from duplicate groups (they have no `source.ref`).
129. **Round 3 re-audit fix: seal lookup is a set.** Step 7 searched the sealed list of the next succession for every record, which is O(n²) at the 230,000-record scale and made `verify` of a large rotated log take minutes. It now builds one set per succession.

The README tells the person to write the id on the same paper. The spec does not bind the words to the id: the id is public and does not need protection, and a binding would change key derivation.

P2b (no gate) makes that the default for every version. P3 was the text cleanup after P1 and P2; the anneal already folded the change notes into the body. P5 (no P-256) removes the key type that phone secure elements support (EXTENSIONS 11.2, DECISIONS 88), for 60 lines.

Fixed: the AI saw the bean folder path in the instructions and errors (now "the bean folder"); the error named a random bad term when there were several (now the first in order); the new rows named a detail no adapter writes. ## Lens fixes, 2026-10-30

Source: three audits of `2db41d1`, one per value set (simplicity of the core, operability, and validity rules that strangers can implement). No validity rule, record, id, signature or vector byte changes. Validity rules stay frozen until 2026-11-13.

154. **The format freezes at `v` = 0, not 1.** A bump to 1 at the freeze had no rule for `v` 0 records: a verifier that knew only `v` 1 would find every `v` 0 genesis too new, and an identity with records of both versions had no meaning. Freezing at 0 keeps every real record and keeps `v` ≥ 1 for a real rule change, which must say how it treats `v` 0 (SPEC 8.1, CORE 6.4).
155. **Only the local identity being too new stops `gc` and gives exit 3.** Before, any too-new identity did, so a stranger whose files you synced could stop erasure for good with one self-signed genesis of a newer `v`. `gc` erases only targets of valid tombstones, a too-new identity's records are never valid, and only an identity's own keys can make it too new (K1), so a too-new identity cannot change which tombstones of another identity are valid. SPEC 7.6 step 5, 12.1, test 24 and new test 44; CORE 4.1.7.
156. **Superseded by 168. A tombstone carried the purged dedupe ref (`context.purged_ref`).** The verifier does not read it (3.2), so no record changes. `append` reads it from the valid tombstones, so losing `local/` no longer brings purged data back on a re-import. `local/purged-refs.jsonl` stays for purges from older builds and for targets that a sync refused. SPEC 7.7, 7.8, 9.5 and known limit 5.
157. **SPEC sync says what the code does.** Sync copies a file only when it passes steps 1 to 15 (a file of unknown `v` stops at step 13 and passes), and replaces a stored copy that fails them. The old text (steps 1 to 12) let a reformatted copy of a record spread and never heal. A sync size limit with `-max-mb` was added here and deleted in 173. SPEC 4.5, 7.4, 15; CORE 4.1.2.
158. **The leaf grammar is written down as the Go verifier applies it.** Depth: the record object is level 0, and a value deeper than 256 is `bad json` (a MUST, it was a MAY). `type` is ASCII, `source.system` is 1 to 64 UTF-8 bytes, `context.reason` is at most 200 code points. Patterns match the whole string, with ASCII classes. The adapter excludes `@`, space, TAB, LF, FF and CR only. "No blobs" and "no refs" allow an empty array. `value` of a `bean.*` record is exact (3.2 against 3.3). `hlog.*` core types are `old format`, now a short error string. The 10,000-node SHOULD is deleted: Go has no limit and the tree walk is linear. Ed25519: the key is not checked to be a point, and V23 pins what Go accepts. The second verifier now does the same in each case (`fullmatch`, byte lengths, the adapter set, empty arrays, depth 256, exit 3 only for the local identity, no lines for a too-new identity).
159. **Output follows the SPEC step order.** A retired key's destructive record that the rotation did not seal is `not sealed` (step 7) before `frozen` (step 8). A correction with missing targets gets one `held` line, and none when another target makes it invalid. A too-new identity gets no step 3 lines. `gc` erases a hidden target under any valid tombstone, so two tombstones for one target no longer keep it hidden for good. A tombstone with blobs now fails on `blobs`, not `value`. `import-export` checks a blob's name before it writes it.
160. **Deleted:** `reindex` and `local/cache/index.json` (nothing read it; SPEC 7.10 is now about caches), `docs/history/` (git has it; `UPGRADING.md` keeps the changes that matter to a user), the private meeting references and names in SPEC, ROADMAP and the code comments, the steward lines of SPEC 19 ("No person or company owns bean"), the unbuilt `-p256` flag line and Extension 1 error strings, vectors V13 to V16 that were never published (V24 conformance folders replace them), and stale section references. Test files are named after what they test. `go.mod` pins the toolchain, and `make test` runs `-race -failfast`.
161. **Not done here, with the reason.** Counting identity records outside the chain as valid changes the valid-set output and needs a definition of "valid" for identity records. The `hlog.*` rule and every narrowing (strict times, a strict Ed25519, the canonical check before the version gate, a signing key that is also a recovery key) change validity, so they wait for the freeze to end and a scan of the real log. (The owner merged the narrowings early, in PR #10: 162 to 165.) A single key kind in `Report.Errors`, the same field rules for seals and successions, and splitting `checkFields` and `main` change output or validity or only move code. Moving SPEC 12.3 into COMMANDS.md and making CORE the spec are larger edits than this pass. `bean verify -n` is replaced by the copy drill in UPGRADING.md, which needs no code. Dropping P-256 and making `-nostr new` the default change validity or CLI behavior (151).

## Narrowed rules, 2026-10-30

Source: the same three lens audits. Each change makes some records invalid that were valid before. That can make other records valid: a halting record that becomes invalid un-halts its identity, and a tombstone that becomes invalid restores its target. bean's own writers never made an affected record. The copy drill in UPGRADING.md shows every change on a real log (`tools/narrowscan` was deleted in 174). Validity rules were frozen until 2026-11-13, so this lands only when the owner decides. The owner merged it on 2026-10-30 (PR #10).

162. **N1: one time syntax.** "RFC 3339" left case, the comma, the offset range, year 0000 and the fraction length open, and Go's `time.Parse` and Python's `datetime` read it differently. SPEC 3.5 now gives one pattern and the ranges, and `end` and `start` compare exactly. `core.ParseTime` is the pattern plus `time.Parse`; `ParseWhen` and the CSV importer use it, so a writer cannot make a record that the verifier rejects. Conformance cases 05 to 09e.
163. **N2: Ed25519 as libsodium checks it.** Go's `crypto/ed25519` accepts small-order and non-canonical keys, so the identity point had one signature for every id, and a libsodium verifier disagreed (SPEC 17 item 12). Keys must be canonical points that are not of small order, and R must not be of small order. The check is a decode plus a table of the five small-order y values in `core/edpoint.go` (170). It runs once per key (remembered), and the R check is the same lookup, so `verify` stays as fast as before. The object cache got a rules line, so a cache written before N2 is not trusted. V23 and conformance cases 18 to 19b and 18d.
164. **N3: canonical bytes before the version.** A reformatted copy of a record of unknown `v` was skipped and synced, and a reformatted head-key record halted the identity (cases 21, 24, 25). JCS does not depend on `v`, so step 13 is now the canonical check and step 14 the version.
165. **N4: a signing key is never a recovery key.** 5.8 could be read two ways, and Go accepted a succession whose new key is the recovery key that signed it or its own next recovery key, which lets the daily key write successions (cases 17 and 17b). The same holds for a genesis. A revealed recovery key used as a bare-key author (case 17c) stays valid: it is its own author, not the identity.
166. **The `hlog.*` rule stays.** Deleting it loosens validity: old `hlog.succession` and `hlog.tombstone` files would become valid claims, which older builds reject, and the person who still has a pre-rename log would lose the `old format` hint that UPGRADING.md promises. Since the lens fixes the rule is in SPEC 3.3 and both verifiers apply it, so there is no split left to fix. Keeping it is the smaller change.
167. **Not narrowed:** P-256 stays verify-only and the 10,000-node depth limit stays deleted. Neither has a real record behind it.

## Second lens round, 2026-10-30

Source: a second audit of the lens fixes and the narrowed rules, one per value set. Only 172 changes validity. The copy drill in UPGRADING.md shows its effect on a real log.

168. **A tombstone carries no dedupe ref again.** `context.purged_ref` (156) synced to every copy, so anyone with the identity secret could test guesses of what the person deleted against it. No simple replacement leaks nothing: the target id does not link to a re-import, and the hidden file is gone after `gc`. So `local/purged-refs.jsonl` is again the only record of a purged import, and README, SECURITY and SPEC 7.8 say to back it up. A copy that never had the target, or that lost the file, imports the same source data again as a new record (SPEC 17 item 5). Tombstones written by the build of 2026-10-30 keep the field; nothing reads it.
169. **`gc` erases a target that another valid tombstone still purges.** The hold entry names one tombstone. When that tombstone became invalid and another valid tombstone still purged the target, `gc` kept the target hidden for good. `gc` now asks only whether the target is purged and hidden. SPEC 7.6 step 5.
170. **The Ed25519 small-order check is a table.** A key or an R is of small order exactly when its y is one of five values (0, 1, p−1 and the two y of the points of order 8). The table replaces the point doubling in `core/edpoint.go`. No result changes: a test compares the table with the doubling on 24,142 keys, and a one-off run agreed with libsodium's `crypto_core_ed25519_is_valid_point` on every key it accepts or refuses for a reason other than its subgroup check.
171. **A hidden target of a too-new identity gets no `hidden pending gc` line.** 8.2 reports nothing for a too-new identity. Output only. SPEC 6.7 and 7.6 step 6.
172. **N4 covers the whole path.** A succession could name a current or earlier signing key, or a recovery key that the chain already committed to, as its next recovery key, so a retired (possibly stolen) device key could come back as the key that rotates. Now a succession is `recovery not advanced` when its `value.recovery` is already on its path, and `key reuse` when its `value.key` is a key on its path or commits to its own or any earlier `value.recovery`, or when its `value.recovery` commits to a key on its path. Go and the second verifier check in that order. bean's writers derive each recovery key from the seed, so they never made such a record. This makes some records invalid and can make others valid (a key that the invalid succession would have retired stays the head). Conformance cases 27a to 27f, SPEC 5.8, CORE 3.1. The validity freeze ran to 2026-11-13; this lands only when the owner merges it.
173. **`sync -max-mb` is deleted.** About two million records would pass the 2 GiB default, far past what fits in memory, and rsync or Syncthing go around it anyway. SECURITY keeps "sync only from your own copies".
174. **The copy drill is the one way to check an upgrade.** `tools/narrowscan` re-implemented the old rules by hand and showed only direct hits, not records that become valid or unresolved as a result. The drill in UPGRADING.md builds the new binary beside the old one in a new `mktemp -d` folder, runs both on two copies of the log and prints the full difference of the verify lines and of the valid records (`ls -all -json`).
175. **An agent-only copy whose person's genesis is gone says `own identity missing`**, as the person's own copy does (142). It exited 0.
176. **SPEC text that gave a different answer from the code.** 5.8 now says which recovery-key records are invalid (conformance 17c is valid: a recovery key as a bare-key author is an ordinary bare key). 6.7: a tombstone whose target has a too-new author or subject is held, so `gc` never erases it. 3.5: `-00:00` means `Z`. 6.3: "unresolved author" and "unresolved subject" apply to an id that names no identity, which includes a genesis that starts none. No rule changes.
177. **Cleanup.** The owner's name and private answers are gone from this file, test comments cite DECISIONS numbers or SPEC sections in place of audit labels, a test fixture is named `cloud`, `vectors/conformance/README.md` says how to use the folders, `core.Version` is 0.6.0, the export manifest says `bean-v0`, and SPEC 17 items 10 and 11 are shorter. Nothing reads the manifest string.
