# Instrument evidence — minimum viable contract

Status: **draft design and implementation hypothesis, not a standard**. No code implements this document. No change to Bean core v0 is proposed.

## Purpose

Prove one property before designing anything broader:

> An instrument commits to the bytes it actually acquired, gives those bytes and its signature to the person, and an independent program verifies both without the manufacturer.

The person may then preserve the unchanged proof in Bean and later disclose it selectively. This is the initial product requirement, not a requirement to create a new cryptographic or health-data standard.

## The decisions

1. **Source-independent receipt.** The instrument need not know a patient's name, account or Bean subject identifier before measuring. It signs a receipt about a capture, not a claim about a named person.
2. **Original evidence first.** The receipt binds exact raw byte sequences and the acquisition configuration required to parse them. Digest and byte length are checked *before* conversion, processing or interpretation. Calibration or other material necessary for an intended numerical result must also be bound. No implicit or external dependency is acceptable for offline replay.
3. **Real trust boundary.** A signature made by host software after the host receives mutable data is a *host claim*, not proof that the instrument produced those bytes. First map the ADC/FPGA/MCU/host path and establish the earliest point where bytes and hashes can be protected from later alteration. Software-only signing is a permitted prototype, with its weaker assurance stated accurately.
4. **Owner adoption is a separate event.** The person owns the original receipt and raw artifacts. A normal owner-signed Bean claim references the unchanged receipt and stores its evidence in encrypted Bean blobs. The owner never impersonates the instrument or changes its original signature.
5. **Verification is independent of trust.** A signature establishes which key signed. It does not establish a manufacturer's identity, a calibrated device, biological accuracy, or trustworthy time. Report these as separate outcomes.
6. **Portable by construction.** Proof, evidence, formats and verification software work offline, using a CLI, with no AION account, API, subscription, token, relay or key-escrow service.
7. **No core changes or premature standardization.** Implement one physical proof. Only after a second independent verifier agrees and real hardware succeeds should the receipt format be proposed for freezing.

## Only three artifacts for the first proof

| Artifact | Signed by | Role |
|---|---|---|
| **Capture receipt** | The signer inside the measured acquisition trust boundary, if one exists | Commits to evidence hashes, byte lengths and acquisition context |
| **Raw evidence and acquisition context** | Not independently signed; cryptographically bound by the receipt | Exact captured signal bytes and information required to interpret them |
| **Owner adoption claim** | The person, using ordinary Bean signing | Records ownership, receipt digest and storage locations, without rewriting instrument authorship |

For the first proof the evidence may be one small raw file plus one acquisition-settings file. Chunk only when a real capture cannot be handled as one bounded file. Avoid a Merkle tree, global sequence log, witness network or device registry until partial verification or omission detection demonstrably requires one.

The receipt should contain no patient identifier by default. A stable device public key can still make captures linkable; therefore, never publish receipts or plaintext Bean records to an unrestricted relay.

## Minimal receipt information

The initial receipt needs only:

- **Domain/profile discriminator** preventing a signature from being mistaken for an unrelated signed statement.
- **Capture identifier**, generated by the signer; random and collision-resistant. A capture ID is not a trusted timestamp.
- **Signer public-key identifier**, with a deterministic way to extract or locate the public key.
- **Complete artifact table**: ordered role, exact byte length and SHA-256 of each required file. Include at minimum raw acquisition bytes and a documented acquisition configuration. Calibration, firmware or processing data are included *when necessary*, as artifact hashes, not as unverifiable marketing labels.
- **Completion indicator**: only successfully finalized acquisitions may be reported complete.

The receipt is valid only if the signature and *every* required artifact hash and length verify. A missing calibration needed for quantitative interpretation must prevent a replay/accuracy claim even when capture integrity itself passes.

**Encoding/signature format is deliberately provisional.** Prefer established COSE_Sign1 (RFC 9052/9053) with deterministic CBOR (RFC 8949) if it fits the selected signing hardware and an audited library exists. Evaluate existing equivalent formats before adopting COSE. Use Ed25519 or hardware-supported P-256 through established libraries. Do not invent a signing algorithm or require both algorithms in v1. Document exact bytes and publish vectors for whichever single profile the first real instrument uses. No final COSE field map, key-ID encoding, clock field or size constant is ratified by this document.

If the signing boundary cannot authenticate the bytes being hashed, do **not** claim device-native evidence. The first working version can be marked "software-signed, host-controlled" while the acquisition chain is improved.

## End-to-end behavior

### Capture

1. Identify the trustworthy acquisition boundary and the owner of the signing key. Record its limitations.
2. Capture one actual instrument signal and its machine-readable acquisition settings, preserving exact bytes, sample order, sampling rate, endianness and other required details.
3. Compute byte lengths and SHA-256 as close to that acquisition boundary as physically possible, and sign the finalized artifact manifest before downstream host modification is possible.
4. Deliver receipt and evidence locally, with a verifier-readable format document. No network dependency.

### Verify

An independent implementation:

1. Parses the receipt using explicit limits and checks its signing domain, key, algorithm and signature.
2. Streams every declared artifact, verifying exact length and SHA-256. Detects missing, substituted, truncated or reordered material.
3. Reports separate results: **signature validity**, **evidence completeness**, **source-key trust**, **replay availability**, and **scientific/clinical validation status**.
4. Reproduces one stated numerical output only when all the requisite acquisition context, method and inputs are present.

The verifier must not confuse a valid self-signed key with an AION-manufactured device. Without a recognized pairing or offline attestation, source trust is **unestablished** even when the signature is valid. A verifier without a prior checkpoint cannot detect that an entire separate capture was withheld.

### Preserve in Bean

1. Preserve original receipt bytes, raw data and settings in the person's controlled store, encrypting with current Bean blob semantics.
2. Write an ordinary owner-signed record such as `instrument.ingest`, referring to the original receipt SHA-256 and encrypted blob IDs. The receipt hash is over its *original* bytes, not over ciphertext; the Blob IDs are storage addresses, not evidence hashes.
3. Re-export to a different machine and verify that the receipt and evidence remain byte-for-byte identical.
4. Do not modify Bean core identity, record validity, key rotation, or encrypted-blob formats.

### Share — only after the first physical proof

A user selects a subset of complete proofs and sends an encrypted package to a chosen recipient, using a standard recipient-encryption construction and distinct encryption keys. The recipient decrypts and runs the same offline verifier. No full-log disclosure or online AION authorization is needed. A recipient's saved plaintext cannot be revoked retroactively. This is a second milestone, not a prerequisite for signing a real acquisition.

## Minimum adversarial tests

| Test | Expected outcome |
|---|---|
| Exact receipt and exact source bytes, offline | Signature and evidence complete |
| One-byte raw, settings or calibration mutation | Explicit hash failure |
| Truncated, extended, missing, misordered or duplicate file | Incomplete / invalid; never silently accepted |
| Altered signature, wrong key or unsupported algorithm | Signature invalid / unsupported |
| Self-signed stranger device | Signature may pass; source trust unestablished |
| Replayed receipt | Same proof; freshness unknown without local anti-replay state |
| Host replaces samples after device signed | Evidence check fails |
| Host signs fabricated samples itself | Report host-software assurance, not hardware-device assurance |
| Original bytes pass between two independent verifiers | Same signature and evidence verdict |
| Original bytes exported from Bean to another computer | Same proof and independent result |
| All network access disabled, AION unavailable | Signature/evidence verification succeeds |
| Missing method or material needed for numerical replay | Integrity may pass; replay explicitly unavailable |

Use synthetic fixtures for negative cases, but **one actual AION acquisition** to demonstrate the positive case. Test physical accuracy, repeatability and calibration with experimental controls separately from cryptographic tests.

## Scope limits and open gates

**Do not build yet:** universal medical ontology, device reputation, manufacturer trust registry, blockchain, public relays, global witness/consensus, hypothetical firmware attestation, multi-recipient permissions, encrypted-sharing SDK, or elaborate derived-result DAGs.

The decisions that *must* be grounded in hardware rather than assumed:

- Where do signal bytes first become available, and which component can hash and sign them without trusting later mutable host software?
- Which real raw file, acquisition settings, calibration assets and one reproducible computation will form the first fixture?
- What signing key mechanism, standard receipt format and library are already feasible on that hardware?

When a new capability is proposed, the test is: **Does it directly make the first verifiable evidence loop work without AION?** If not, defer it.

## Architectural references, not required dependencies

- RFC 9052 and RFC 9053: COSE signature formats and algorithms.
- RFC 8949: deterministic CBOR encoding.
- RFC 9334: RATS distinctions among evidence, endorsements, verifier and relying-party policy.
- RFC 9180: HPKE, for a later selective-sharing milestone.
- FHIR Provenance and W3C Verifiable Credentials: interchange adapters where useful, not substitutes for the original raw-acquisition proof.
